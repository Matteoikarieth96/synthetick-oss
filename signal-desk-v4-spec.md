# SyntheTick v4 — Platform Build Specification

**Deliverable:** a full rearchitecture of SyntheTick from a single-file demo into a real platform with a genuine asset universe.
**Brand (2026-07-15, user decision):** the product is **SyntheTick** (rebranded from Signal Desk), served at **synthetick.org**. The wordmark is camel-case SyntheTick everywhere in user-facing copy, docs and GitHub; the ".org" appears only when referring to the domain itself. Internal identifiers deliberately keep legacy names to avoid breakage: `public/signal-desk.js`, `sd-auth.js`, `SIGNAL_*` env vars, `sd-*` localStorage keys, and this spec's filename.
**Status note (2026-10, open-source release):** this started as the design document and was amended section by section as the product shipped. Sections 1 to 11 keep the original design wording: where they mention Supabase Edge Functions, Vercel or the retired EODHD vendor, the implementation differs. It runs as a single Node server (`server/server.ts`, section 12), the vendor plan used for equities has ended (section 17), and the ingest code still assumes that one vendor (a vendor-neutral adapter is an open contribution). **Sections 12 to 18 describe what runs today and win over earlier sections.**

**Audience:** Claude Opus 4.8 or a developer. Follow exactly; where unspecified, prefer the simplest implementation consistent with §2.
**Decisions locked:** Supabase backend (not static snapshot) · paid equity vendor **FMP Ultimate** (decision 2026-07-10: replaces EODHD, which lacked Borsa Italiana; **EODHD retired 2026-07-10/11** — legacy code paths removed; the shared cross-listing dedup lives on in `ingest/lib/dedup.ts`) · bonds scoped to **bond ETFs + major sovereign benchmark ETFs** (no individual bonds in v1) · **China scoped to ADRs + HKEX** (A-shares deferred, see §4.1a) · **one row per company** via cross-listing dedup (§4.1b) · **market caps normalized to USD** at ingestion (§4.1c).

## 0. Product definition

Given a source document (PDF, pasted text, tweet, YouTube link, screenshot, or a voice note — recorded in the browser or uploaded as an audio file), the platform:

1. Elaborates a structured **investment thesis** (summary, stance, anchors, themes) with **binding requirements** extracted from the user's words.
2. Matches the thesis against a **real universe**: most listed stocks and ETFs in the **US, Europe and China**, bond ETFs/sovereign benchmarks, and **crypto listed on CEXes and DEXes**.
3. Returns up to 10 ranked assets with an alignment gauge (0–100, absolute), a specific 3-sentence analysis each, complement/competitor mapping relative to the user's holdings, **real prices and real 30-day charts** (start / 30-day average / latest close annotated directly on the sparkline — the average as a dashed level labeled with the bare value, the latest close colored green/red vs the START price, 2026-07-08), and real venues. ETF/bond-ETF cards additionally show the fund's **portfolio** (PR #10): top holdings with weights + one breakdown (sector, else asset-allocation, else region), rendered only when the vendor supplies it — never inferred.
4. **Never violates a user requirement.** "Only crypto" can never show a stock. If nothing qualifies, it says so.

Non-goals for v1: individual corporate/government bonds; derivatives; portfolio tracking; trade execution; personalized financial advice. Every screen keeps the disclaimer: research starting point, not a recommendation.

## 1. Architecture overview

```
┌────────────── INGESTION (scheduled, GitHub Actions cron) ──────────────┐
│ FMP (stocks/ETFs US·EU·CN)   ─┐                                        │
│ CoinGecko (tokens + CEX venues)├─► normalize ─► embed (Voyage) ─► DB   │
│ GeckoTerminal (DEX pools)     ─┘                                        │
└─────────────────────────────────────────────────────────────────────────┘
┌────────────── RUNTIME ──────────────────────────────────────────────────┐
│ Frontend (Next.js on Vercel, or the existing single-page UI)            │
│   └─► Supabase Edge Functions (all secrets live here)                   │
│         ├─ /thesis      Claude: structured thesis + requirements        │
│         ├─ /candidates  SQL hard filter → pgvector top-100              │
│         ├─ /select      Claude rerank: 10 picks + scores + relations    │
│         ├─ /audit       deterministic + Claude compliance audit         │
│         ├─ /analysis    Claude per-asset 3-sentence analysis            │
│         └─ /market      FMP & CoinGecko live quotes + 30d OHLC          │
└─────────────────────────────────────────────────────────────────────────┘
```

Principles: **secrets never reach the browser** (all vendor keys + the Anthropic key live in Edge Function env vars); **hard constraints are enforced in SQL and re-audited in code** — the LLM proposes, deterministic code disposes; every LLM output is validated JSON with a fallback.

## 2. Stack

| Layer | Choice | Why |
|---|---|---|
| Database | Supabase Postgres + **pgvector** | free tier fits ~40k rows + embeddings; REST + RPC built in |
| Server logic | Supabase **Edge Functions** (Deno/TS) | keeps keys server-side; no separate host |
| Frontend | **Next.js 16 App Router** | keep the v3 design system (§9); migration starts with a server-rendered app shell while the existing browser interaction layer is incrementally converted to React components (2026-07-10) |
| Equities/ETF data | **FMP** (paid plan) | screener + profiles (ISIN, HQ domicile, `isAdr`) + ETF holdings/weightings + EOD/delayed quotes for US, all major EU exchanges **incl. Borsa Italiana**, HKEX. Uses the `/stable/` API only (legacy `/api/v3/` is dead for post-2025-08 accounts) |
| Crypto data | **CoinGecko** free API | ~15k tokens, descriptions, categories, per-coin CEX tickers |
| DEX data | **GeckoTerminal** free API | pools per token → DEX venue flags |
| Embeddings | **Voyage AI** `voyage-3-lite` (Anthropic-recommended; OpenAI `text-embedding-3-small` acceptable) | computed once per asset at ingestion; pennies per full run |
| LLM | **OpenRouter** (`anthropic/claude-sonnet-4.6` by default; model configurable via `SIGNAL_LLM_MODEL`) | thesis, rerank, audits, analysis, vision extraction; web search via OpenRouter's `:online` suffix. Decision (2026-07-06): OpenRouter replaces the direct Anthropic API — one key, provider flexibility, same models. |
| Scheduler | GitHub Actions cron | free; nightly crypto, weekly equities |

Estimated running cost: FMP paid plan · Supabase $0 (free tier) · Voyage/embeddings <$5 per full re-embed · Anthropic per-use (~5–7 calls per research run).

## 3. Database schema

```sql
create table assets (
  id            bigserial primary key,
  ticker        text not null,             -- display symbol (AAPL, ETH, ASML.AS)
  vendor_id     text not null,             -- FMP symbol (Yahoo-style: AAPL, ENI.MI), CoinGecko id, or Sacra company domain (unique per source)
  source        text not null,             -- 'fmp' | 'coingecko' | 'sacra' ('eodhd' = legacy rows, retired after FMP backfill)
  name          text not null,
  kind          text not null check (kind in ('stock','etf','bond','crypto','private')),
  region        text not null check (region in ('us','eu','cn','other','global')),
  exchange      text,                      -- primary listing (stocks/ETFs/bonds)
  cex_venues    text[] default '{}',       -- crypto: Binance, Coinbase, Kraken…
  dex_venues    text[] default '{}',       -- crypto: Uniswap v3 (Ethereum), Aerodrome (Base)…
  cap_class     text check (cap_class in ('mega','large','mid','small','micro')),
  market_cap_usd numeric,                  -- ALWAYS USD (converted at ingestion, §4.1c); kind='private': latest estimated valuation (§4.2b)
  volume_24h_usd numeric,                  -- CoinGecko 24h USD volume; crypto only
  isin          text,                      -- dedup key for cross-listed equities (§4.1b)
  listings      jsonb default '[]',        -- secondary listings: [{exchange, ticker, currency}]
  accessibility text default 'open'
                check (accessibility in ('open','restricted')),  -- 'restricted' = A-shares etc., excluded by default (§4.1a)
  sector        text,                      -- GICS sector / CoinGecko primary category
  industry      text,
  categories    text[] default '{}',       -- tags: 'AI', 'Layer 2', 'uranium', 'UCITS', 'Italy'… CURATED scope tags only —
                                           -- they feed the §5.2 +0.15 semantic boost; never per-holding tickers/names
  description   text,                      -- the text that gets embedded
  etf_portfolio jsonb,                     -- ETFs/bond ETFs (PR #10): {holdings_count, top_holdings[{symbol,name,weight}],
                                           -- asset_allocation/sector_weights/region_weights[{name,weight}]} normalized from
                                           -- vendor ETF data; null = no vendor data (no '{}' default — one empty state).
                                           -- FMP (live-verified 2026-07-10): etf/holdings rows {asset,name,isin,weightPercentage};
                                           -- etf/sector-weightings weights are numbers, etf/country-weightings weights are
                                           -- STRINGS with a trailing "%" — parse both; country breakdown fills region_weights.
                                           -- Fund facts (2026-07-12): the same etf/info call also carries expense_ratio
                                           -- (percent units: 0.2 = 0.20%), avg_volume (shares), inception_date, nav +
                                           -- nav_currency, issuer (etfCompany), domicile — stored here at ingest at zero
                                           -- extra vendor cost; existing rows fill over the ~6-day refresh cycle. The card
                                           -- shows expense_ratio in the metrics row and the rest under "Fund facts" in the
                                           -- detailed-analysis toggle; missing values render "—"/are omitted, never guessed.
                                           -- No asset-allocation equivalent on FMP; that slice is empty for source='fmp'.
  website_url   text,                      -- project/company website from the source vendor
  logo_url      text,                      -- vendor-hosted logo image (2026-07-13): FMP profile.image (null when
                                           -- defaultImage=true — that's FMP's generic placeholder), CoinGecko
                                           -- markets image. Both CDNs are public/hotlinkable (verified: US, .MI,
                                           -- .HK, ETFs). Sacra has no logos → null; the card falls back to the
                                           -- website_url favicon, then to ticker initials. Zero extra vendor calls.
  is_active     boolean default true,      -- delisted/dead assets flip false, never deleted
  currency      text,
  updated_at    timestamptz default now(),
  unique (source, vendor_id)
);
create index on assets (kind, region, cap_class) where is_active;
create index on assets using gin (categories);

create table asset_embeddings (
  asset_id   bigint primary key references assets(id) on delete cascade,
  embedding  vector(512),                  -- voyage-3-lite dimension
  model      text not null,
  updated_at timestamptz default now()
);
create index on asset_embeddings using hnsw (embedding vector_cosine_ops);
```

`kind='bond'` = bond ETFs and sovereign-benchmark ETFs only, identified at ingestion by FMP `etf/info.assetClass == 'Fixed Income'` when present, else the bond/fixed-income/treasury/gilt name regex (`categories` gets `'bond-etf'`). (`etf/info` is missing for some cross-listed lines — AGGH.MI returns empty — hence the layered check.)

## 4. Ingestion pipeline (repo: `signal-desk-ingest`, GitHub Actions)

### 4.1 Equities & ETFs — FMP (weekly, Sunday)

**Implementation note (v4.1, FMP migration 2026-07-10):** FMP Ultimate has **no daily credit quota** (3,000 calls/min, 150GB/30-day bandwidth), so the EODHD credit-budget machinery (`EQUITIES_FUND_BUDGET`, 402 short-circuit, multi-day backfill) is retired. The pipeline reshapes because FMP splits data differently: the **screener** lists symbols per exchange (with `isEtf`/`isActivelyTrading`/country, but NO ISIN or currency, and `marketCap` in an unreliable mix of currencies — never noise-floor on it), the **profile** carries everything dedup and mapping need (ISIN, HQ-domicile `country`, `isAdr`, cap+`currency`, sector/industry, description, website), and **ETFs take 4 extra calls** (`etf/info`, `etf/holdings`, `etf/sector-weightings`, `etf/country-weightings`). Flow: screener sweep → profile sweep (all candidates; ~14 min at pace) → ISIN dedup → skip fresh rows (<6 days, saves embeds) → ETF enrichment → upsert+embed in batches. Deactivation still only on full-universe runs. Cron stays daily.
1. Pull screener symbol lists per exchange (FMP codes): **US** (NYSE, NASDAQ, AMEX), **EU** (LSE, AMS, PAR, BRU, LIS, XETRA, SIX, BME, **MIL — Borsa Italiana, added by the FMP migration**, STO, CPH, HEL, OSL, VIE, DUB), **China** (HKSE + US-listed ADRs flagged `region='cn'` by domicile; SSE/SZSE deferred per §4.1a).
2. Filter: keep `isEtf` or plain stock rows (drop inactive lines); drop **true mutual funds only — FMP's `isFund` flag is NOT "mutual fund" (2026-07-29):** it also marks exchange-traded products whose `isEtf` is false (USO, IAU — the $59B iShares Gold Trust), REIT common stock (ESS, FRT, VNO), closed-end/investment trusts (PDI, SMT.L), and even the odd bank (CTBI) — all live-verified; a naive `!isFund` drop silently removed every one of them from the universe. A true mutual fund is an `isFund` row that never prints on-exchange volume (all 4,390 X-suffix NASDAQ fund share classes report zero/absent screener volume) or matches the 5–6-letter X-suffix share-class symbol shape (VTSAX, QCGRIX). Also drop warrants/rights/SPAC units; the $50M USD noise floor applies **after** the profile fetch (profile cap is local currency + explicit `currency` → FX-convert, then floor).
3. Per symbol fetch the profile: name, sector/industry, description, market cap, currency, ISIN, HQ country, `isAdr`, website. ETFs additionally: info/holdings/sector-weightings/country-weightings. UCITS flag for EU ETFs. **ETP classification probe (2026-07-29):** a surviving `isFund` row with `isEtf=false` gets the ETF fetch bundle as a probe — FMP's `etf/*` endpoints answer for genuine exchange-traded products (USO, IAU) and stay empty for the mislabeled stocks sharing the flag (REITs, CEFs, banks) — so one call both classifies the line (hit → `kind='etf'`, fund AUM, portfolio; miss → stays a stock) and fetches its fund data. **Country scope tag (2026-07-10):** `categories` gets `'Italy'` for Italian-domiciled assets (HQ domicile `IT`) and for ETFs whose name marks Italy exposure (`Italy`/`Italian`/`FTSE MIB`) — Italy ETFs are usually IE/LU-domiciled funds, so the name regex is the only signal. Feeds the §5.2 +0.15 boost and the embed text so "Italian stocks/ETFs" theses surface Borsa Italiana names.
4. Map: `region` from `profile.country` (already HQ domicile — no listing-country workaround needed); `cap_class` bands: mega >$200B, large $10–200B, mid $2–10B, small $300M–2B, micro <$300M.
5. Upsert on `(source, vendor_id)` with `source='fmp'`, `vendor_id` = FMP symbol (Yahoo-style); symbols missing from the new list → `is_active=false`.
   **Deactivation deletes the row's embedding (2026-07-12).** An inactive row's vector can never surface (§5.2 joins on `is_active`) but it stays in the HNSW graph and slows every retrieval — the retired-EODHD backlog left 42% dead vectors (28.4k total, 16.4k active) and pushed `match_candidates` past Supabase's ~8s statement timeout (live incident 2026-07-12; ETF-filtered query at 5.1s warm). `deactivateMissing` therefore ends with `sweepInactiveEmbeddings()` — a catch-all that deletes embeddings of ANY inactive asset, not just this run's batch, so crash windows and other deactivation paths (pre-IPO IPO-graduation §4.2b, manual cutovers) self-heal on the next nightly run; the pre-IPO ingest calls it after its own deactivations too. Re-activated rows re-embed through the normal upsert path. After a BULK deactivation, additionally run `reindex index asset_embeddings_hnsw_idx;` in the SQL editor — deletes leave tombstones in the HNSW graph.

Expected volume: ~6k US, ~6k EU, ~1.5–2k CN (ADRs + HKEX), ~3k ETFs.

### 4.1a China scope (v1): ADRs + HKEX only
"China" in v1 means the **investable** universe: US-listed Chinese ADRs (BABA, PDD, NIO…, `region='cn'` by domicile) and **HKEX** listings (Tencent, BYD, Meituan…). **A-shares (SSE/SZSE) are deferred**: they are largely not directly buyable by ordinary US/EU retail investors, and their thin/Chinese-language descriptions embed and match poorly. Recommending assets users cannot buy breaks the "where to buy" promise. If A-shares are ingested at all in v1, set `accessibility='restricted'` and **exclude them by default** in `/candidates` (`and a.accessibility='open'`); a later phase can expose an "include restricted markets" toggle. ADR/HKEX dual-listed pairs (e.g. BABA / 9988.HK) dedup per §4.1b with the ADR as primary.

**Implementation note (v4.1, FMP):** FMP's `profile.country` is already the **HQ domicile** (BABA → `CN` with `isAdr: true`, live-verified 2026-07-10), so the EODHD listing-country workaround (`AddressData.Country` fallback chain) is gone; region derives from `profile.country`, falling back to ISIN prefix. The `isAdr` flag also replaces the name-regex ADR detection as the primary signal in dedup (regex kept as fallback for unflagged lines). Borsa Italiana (MIL) is covered — verified down to EGM micro caps (CY4GATE, Digital360).

### 4.1b Cross-listing dedup: one row per company
Many companies trade on several exchanges (ASML: Euronext Amsterdam + NASDAQ; SAP: Xetra + NYSE; Siemens: Xetra + OTC ADR). Naive ingestion creates duplicate results and ambiguous region audits. Rule:
1. Group symbols by **ISIN**. **ADR caveat (v4):** a US ADR line usually carries a *different* ISIN from the home line (e.g. ASML.AS `NL0010273215` vs the NASDAQ ADR `USN070592100`), so ISIN alone will not merge them. Add a second-pass merge on **normalized core name** — lowercase alphanumerics with the `ADR` marker and legal suffixes (N.V., NV, Inc, PLC, S.A., AG, Ltd, Holding-as-standalone) stripped — that folds two ISIN groups into one company **only when** their ISIN-country prefixes differ (a genuine cross-border pair) or one member's name contains `ADR`. This targeting avoids false merges of same-country same-name issuers. Missing-ISIN symbols fall back to normalized name + country as before.
2. Keep ONE canonical row. Primary listing = the **home exchange** (exchange in the company's country of domicile); if none, the most liquid listing. `region` follows **domicile**, not listing venue — the ASML row is `region='eu'` even though an ADR trades on NASDAQ, so "only European stocks" correctly includes it and the audit is unambiguous.
3. All other listings go into `listings` (exchange, local ticker, currency) and render in the UI as additional "also trades on" venues.
4. `/market` quotes the primary listing; secondary listings are display-only in v1.
5. **Share classes (2026-07-10):** one company often lists several classes under *different* ISINs (GOOGL `US02079K3059` / GOOG `US02079K1079`; BRK-A/B; HEI/HEI-A), and FMP names both lines identically — no "Class A" marker exists to match on. Classes of one issuer share the **ISIN issuer prefix** (country + first 6 NSIN chars: `US02079K`), so a stage-3 fold merges **stock** groups (never ETFs — acc/dist fund classes are distinct products) with the same issuer prefix AND the same **full normalized name** + HQ country into one company. (Full name, NOT the suffix-stripped core: sequential-ISIN countries reuse prefixes across issuers, and core-stripping "Holding" would merge Heineken N.V. with Heineken Holding N.V. — distinct companies.) The **most liquid class** (screener volume) becomes canonical; other classes land in `listings` like any secondary line, so the card shows one company with its classes as venue options.
6. **Ghost duplicates (2026-07-29):** FMP occasionally carries a stale duplicate of a listing under a dead symbol with the SAME ISIN/CUSIP/CIK but an outdated share count and description (EchoStar: `ECHO` still described the pre-merger DISH business yet out-printed the real `SATS` line on screener volume — so the volume tiebreak made the ghost canonical and deactivated the real line, live incident found 2026-07-29). Guard: at the home-exchange rung of the canonical pick, when a same-currency rival's profile market cap is decisively (**≥1.5×**) larger than the volume leader's, the larger-cap line wins. Share classes are unaffected — GOOG/GOOGL report near-identical company-level caps, nowhere near the 1.5× bar.

### 4.1c Currency normalization
EU/HK quotes arrive in EUR, GBP, GBX, CHF, DKK, SEK, NOK, HKD. At ingestion, convert every market cap to **USD** (`market_cap_usd`) — cap-class bands (§4.1 step 4) are meaningless otherwise (GBX is pence: divide by 100 before converting). FX source (changed 2026-08-03, §17): **ECB rates via frankfurter.dev** (keyless, one call for all published pairs, inverted from USD→CUR), with FMP forex quotes (`batch-quote`, then `/stable/quote?symbol=USD{CUR}` inverse) as fallback for currencies the ECB doesn't publish — FMP forex quotes are a paid feature, so they are never the primary. Prices at runtime display in the **native currency with the code shown** ("€612.40", "HK$342.20"); only caps and cap-class comparisons use USD. The FX table refreshes with each ingest run.

**Embedding language note:** thesis documents may be in any language (Italian, etc.) — Claude handles extraction fine — but asset descriptions are English, so the thesis embedding in §5.2 MUST be computed from the English structured summary produced by `/thesis`, never from the raw document text, or retrieval quality collapses for non-English input.

### 4.2 Crypto — CoinGecko + GeckoTerminal (nightly)

**Implementation note (v4, demo-key quotas):** the CoinGecko demo key allows 30 calls/min and 10,000 calls/month, so nightly full per-coin enrichment of thousands of tokens is impossible (~150k calls/month). Adjusted scheme, same end state: (a) **one-time backfill** fetches detail for the whole target set (~3k coins ≈ 3k calls); (b) **nightly runs** refresh the cheap `/coins/markets` pages for caps/ranks (≈12 calls) plus a **rolling detail budget** (`CRYPTO_DETAIL_BUDGET`, default 200/night ≈ 6k/month) prioritizing new coins first, then the stalest-enriched (tracked via `asset_embeddings.updated_at`); coins beyond the nightly budget get a cap-only partial update that does not overwrite their existing description/categories/venues. Every coin's detail refreshes on a ~2-week rolling cycle.
1. `/coins/markets` paginated: top ~5,000 by market cap (rank cutoff keeps out dust; configurable).
2. Per coin `/coins/{id}`: description, categories, and `tickers[]` → distinct exchange names split into `cex_venues` (identifiers not in the DEX registry) and `dex_venues`.
3. GeckoTerminal top pools per token to enrich `dex_venues` with network qualifiers ("Uniswap v3 (Ethereum)").
4. `region='global'`, `kind='crypto'`, same cap bands. Categories carry over verbatim ('Layer 2', 'DeFi', 'AI agents', 'Ethereum ecosystem' — CoinGecko already tags ecosystems, which directly serves "only crypto related to the Ethereum ecosystem").

### 4.2b Pre-IPO privates — Sacra (weekly, Monday; added 2026-07-10)

> **Vendor key optional.** Pre-IPO rows are read from Supabase; **runtime never calls Sacra** (`marketFor` short-circuits on `source='sacra'`). Without a key the rows do not refresh, and IPO graduates must be pruned from the watchlist by hand. The weekly cron in `.github/workflows/ingest-preipo.yml` ships with its schedule commented out; enable it only with a Sacra plan whose terms cover your use, and store and display only what that license allows.
>
> **Stored series.** Per-company series (valuation, revenue, price-per-share curves, projection scenarios, funding rounds) live in the `assets.private_data` jsonb column (`db/private_data.sql`), loaded by `npm run load:private-data` from vendor files the operator holds under their own data license (`SACRA_ARCHIVE_DIR`, default `./sacra-archive`), with no metered vendor tasks. Vendor news is deliberately not stored: stored news goes stale and misleads, whereas a historical series stays true.
>
> **Consequence for §5.6:** pre-IPO cards previously rendered no chart at all (`series: []` hardcoded). They now plot the stored valuation curve, labelled "Valuation history" rather than "30 day price history" and formatted with `fmtCap`, since the figures are in the billions. `change1d`/`change30d` stay null — a private company has no trading day, and deriving them from revaluation events would misrepresent the number. `asOf` is the date of the latest valuation point, not the row's sync time, which would claim the data is fresher than it is.
>
> **Valuation sanity check.** Some secondary events report the transaction size in the valuation field; the loader anchors on the vendor's latest estimated valuation (dropping trailing points below half of it), or without one drops trailing points that collapse more than 75%, and keeps removed points under `private_data.dropped` for review. The weekly cron path (`latestValuation` in `ingest/sources/sacra.ts`) has only a narrower guard; add the same check before enabling it.

A curated **watchlist** (~25 growth/pre-IPO tech companies, `ingest/run-preipo.ts`) syncs weekly from the Sacra API (`https://sacra.com/api/v1/`, header `Authorization: Token $SACRA_API_KEY`). Sacra covers only ~500–1,000 private companies, so the universe is a hand-picked list of domains — no screener sweep. **Task budget is the binding constraint**: every company touched by a request costs 1 metered task (a plan-dependent monthly quota with a hard cap); the weekly run costs ~2 tasks per watchlist name (company detail + one batched events call), ≈ 215 tasks/month at 25 names — never add per-company news/metrics calls to the cron without re-doing this budget.

1. Per domain `GET /companies/?company_domain=` → slug, then `GET /companies/{slug}/` (detail): description, categories, HQ, founding year, `financials` (latest estimated revenue/valuation/funding), `company_datasets` (valuation & revenue time series), `listings`.
2. One batched `GET /events/?company_domains=…&types=funding-round,secondary-transaction,corporate-action` (last 12 months, citations on): funding rounds, secondary/tender transactions (the pre-IPO market signal), IPO corporate actions.
3. Map: `source='sacra'`, `vendor_id`=domain, `kind='private'`, `ticker`=slug uppercased (display only), `region` from HQ country (US→us, EU/UK/CH/NO→eu, CN/HK→cn, else other), **`market_cap_usd` = latest estimated valuation** (documented proxy: privates have no float; the §4.1 cap bands then classify them for the cap filter and the §5.2 large-cap rescue), `currency='USD'`, `website_url`=domain, `categories` = Sacra category names + `'pre-IPO'` scope tag (feeds the §5.2 boost so "pre-IPO exposure" theses surface these rows).
4. `description` = Sacra description + a generated "Pre-IPO profile" paragraph (latest est. revenue/valuation with dates, total funding, recent funding/secondary events with amounts) — this is the embed text, so recent momentum is retrievable; Sacra rows are **excluded from §4.3b enrichment** (the profile paragraph already plays that role and would be clobbered).
5. **IPO detection**: a watchlist company whose detail shows `type != 'private'` or non-empty `listings` (or an `ipo` corporate-action event) is **deactivated** (`is_active=false`) with a log line — it graduates to the FMP universe on its own; the watchlist entry should then be removed manually. Companies Sacra doesn't resolve (404) are logged and skipped, never fabricated.
6. Upsert on `(source, vendor_id)` + delta embed like every other source. No deactivate-missing sweep (the watchlist IS the universe; absence from a run means an API failure, not a delisting).

Live-API gotchas (2026-07-10): `metric_base` docs examples `revenue`/`arr` are rejected — the real vocabulary is `trailing_revenue`/`run_rate_revenue`; `/categories/` requires a company parameter; profile-level `total_estimated_funding` can lag the datasets — prefer `company_datasets`/events for freshness; some secondary-transaction events report `valuation` EQUAL to the transaction amount (deal size, not company valuation — a $100M Shein share sale is not a $100M Shein), so the valuation refresh ignores secondaries where `valuation == transaction_amount`.

### 4.3 Embeddings (after each ingest, delta only)
Embed `name + kind + sector/categories + ETF holdings/sector names + first 400 chars of description` with `voyage-3-lite` for new/changed assets. ETF portfolio text (PR #10) enters as top-8 holding NAMES + top-6 sector names only — company names carry the semantics; ticker symbols are noise tokens that burn TPM budget. Batch 128 (base tier: 64) AND token-aware — a single request over the 10k TPM cap can never succeed, so batches also split at ~32k chars; full universe re-embed <$5.

### 4.3b Thematic enrichment (added 2026-07-09)
Vendor descriptions for mega-caps and base-layer assets are too generic to connect them to theses that never name them — e.g. an Ethereum/RWA thesis missed ETH entirely because ETH's stored description cosine-sim'd 0.329 vs a ~0.416 retrieval bar; a web-searched "ETH = ~58% of RWA tokenization, ~60% of stablecoins, dominant settlement layer" context lifted it to 0.467 (above the bar). So `assets.enrichment` holds a dense, factual, thesis-agnostic paragraph (LLM + web search) that `buildEmbedText` appends (≤700 chars, labeled `Context:`) so it enters the embedding. Populated by `npm run enrich:descriptions` (ENRICH_TOP_N / ENRICH_KIND / ENRICH_REFRESH) — resumable (enrichment IS NULL only) and fully reversible (null the column + re-embed). ENRICH_REFRESH=true re-enriches the whole top-N with current facts; the GitHub Actions cron (`enrich-descriptions.yml`) runs it every other Tuesday 05:00 UTC (scheduled weekly, gated to even ISO weeks) for top-100 all-kinds + top-100 crypto — needs the `OPENROUTER_API_KEY` GitHub secret. Enrichment feeds RETRIEVAL only; it does not bias the /select alignment score (getting an asset into the pool ≠ getting it picked — /select still judges direct-vs-indirect fit).

### 4.4 Data quality gates
Ingestion fails loudly (Action fails, DB untouched) if: symbol count drops >20% vs previous run; >5% rows missing `kind`/`region`; embedding coverage <98% of active rows.

## 5. Runtime pipeline (Edge Functions)

All LLM calls go through OpenRouter (default `anthropic/claude-sonnet-4.6`), JSON-only prompts, `parseJSON` guard, explicit fallback per step. **Provider resilience (2026-07-12):** every call has a 90-second default timeout (`SIGNAL_LLM_TIMEOUT_MS`) and retries one transient timeout, termination, rate-limit, overload, or 5xx response (`SIGNAL_LLM_RETRIES`, capped at 3). A provider request can no longer hang a research run indefinitely; permanent errors still surface honestly.

### 5.1 `/thesis` — carry over from v3, unchanged in behavior
Input: extracted document text (+ optional user requirements box). 2026-07-06: the extraction prompt now receives the whole document up to a 150k-char safety ceiling (≈37k tokens; beyond that, head + tail are kept, since instructions cluster at document edges) — previously only the first 6k chars. Article/link extraction keeps up to 60k chars of page text (previously 8k), prefers the page's main content container (`<article>`/`<main>`/known content-div classes) over the whole body, and drops repeated nav/boilerplate lines that survive tag stripping. Anchor resolution is strict: explicit/parenthetical ticker exact match (digits legal — HKEX "0700"; an exchange suffix like ".HK" is retried without) → exact name → name prefix (≥4 chars); the old fuzzy `%substring%` first-match via an unsanitized `.or()` string is removed (it produced false anchors, e.g. HYLN from a Lennox document). 2026-07-07: names also generate corporate-suffix/punctuation stems ("Tesla, Inc." → "Tesla Inc" → "Tesla"; "Tencent Holdings Limited" → "Tencent"; "3M Company" → "3M") tried with the same exact→prefix ladder — stems may prefix-match at ≥2 chars since they derive from an explicit longer company name, and market-cap ordering + major-exchange preference (now including "PK" OTC codes) picks the major line. The regex dual-extractor always ran on the full text and still does. 2026-07-07: YouTube links fetch the real transcript via ytscribe.ai (`POST /api/transcripts`, `YTSCRIBE_API_KEY` in .env — never committed) capped at 60k chars, with the video title + author from the payload's metadata prepended (context the bare transcript lacks) and the title used as the source label; when the key is missing, credits are exhausted, or the API fails, extraction falls back to the v3 Claude web-search reconstruction with its `approximate` review warning intact (real transcripts don't carry the flag). Output: `{title, stance, summary, intent(anchor|thematic), direction(long|short), anchors[], avoid[], themes[], requirements}`.

**Copied-link intake (2026-07-08).** Pasting a bare `http(s)` URL into the first-page thesis box does NOT leave the URL as the thesis text; the client intercepts it, calls `/api/extract {kind:'link'}`, and turns the page/video/post into a normal source chip. Clicking "Add link" also opportunistically reads the clipboard during that user gesture; if the clipboard contains a URL, it loads immediately, otherwise the explicit link field opens as before and submits on Enter. For generic articles the server first fetches the page directly and runs readability-lite extraction; if the page is JS-only, blocked, unreadable, or too sparse, it falls back to one web-search-enabled reconstruction call that summarizes the public page substance as source text and marks the source `approximate` so the review card remains the user's checkpoint. X/Twitter still uses oEmbed first; YouTube still prefers ytscribe transcripts before its web-search fallback.

**Proper-name → owner resolution (2026-07-07).** A thesis often centers on a THING rather than a company — a product, model, service, brand, or subsidiary ("MacBook sales will explode", "Grok 4.5 beat every benchmark"). The extraction prompt now resolves such proper names UP the ownership chain to the publicly listed owner and anchors THAT (MacBook → Apple; Instagram → Meta Platforms; Gemini → Alphabet), so the owner is force-included in candidates like any named asset. When the resolved owner does NOT trade publicly, it is returned in a new `private_entities: [{name, note}]` field instead of being silently dropped: the review card shows a "central but not investable — can't be a pick" line (the universe is listed-only, spec §0 non-goals), and listed exposure continues to flow through themes.

**Web-checked entity status (2026-07-07, same day).** Training data goes stale on corporate structure (mergers, IPOs, absorptions — e.g. xAI/SpaceX restructuring), and bare-name DB lookup can't tell the entity a document MEANS from an unrelated listed asset sharing the string ("xAI" → the XAI Octagon credit fund's NYSE ticker). So when extraction yields anchor mentions or claimed-private entities, ONE web-search-enabled call (OpenRouter `:online`, same plumbing as the YouTube path) checks CURRENT facts and does three jobs: (1) `keep` — rejects DB name-collisions among the resolved anchors; (2) `add` — names central entities that ARE publicly traded today as "Company Name (TICKER)", including a listed parent that has absorbed a private company central to the thesis; adds are re-resolved against the DB, and an add that is listed but not in our universe (recent IPO not yet ingested) lands in `private_entities` with a note saying so — never silently dropped, never fabricated as a pick; (3) `private` — central entities not publicly investable today, with a ≤12-word relation note; (4) `corrected_summary` — the extraction writes the summary from training data alone, so it can bake in stale claims that contradict the entity facts on the same card ("since xAI is private…" above a section that knows it's a SpaceX subsidiary): when the summary carries verifiable factual claims that are outdated per the web (ownership, corporate structure, listing status, product/release status, dates), the check returns the summary with ONLY those facts fixed — the user's investment view, direction and scope are never changed or second-guessed — and it replaces `thesis.summary` (which is also what gets embedded, so retrieval benefits); null when already accurate. The review card stays editable, so the user can overrule any correction. Skipped entirely for theses with no named entities (zero cost). Fails open to the resolved anchors + claimed-private list and the original summary. The extraction prompt is unchanged — the web check is the single place current-world facts enter.

**Voice notes (2026-07-07).** The composer accepts spoken theses two ways: 🎙 Record (in-browser MediaRecorder) and ➕ Add file with any audio/video file. Both are normalized CLIENT-side to 16 kHz mono 16-bit WAV via Web Audio (`decodeAudioData` → `OfflineAudioContext`), so any container the browser can play (webm/opus, m4a, mp3, ogg voice notes) works without server-side ffmpeg; cap 10 minutes / ~25 MB decoded. The WAV goes to `/api/extract {kind:'audio'}` → `extractAudio()` → OpenRouter `input_audio` content part against an audio-capable model (`SIGNAL_AUDIO_MODEL`, default `google/gemini-2.5-flash` — the default text model is Claude, which takes no audio). Transcription is verbatim, in the original spoken language (fine per the embedding-language note: retrieval embeds the English structured summary, not the raw transcript). Result becomes a normal source chip; the thesis pipeline runs for any non-empty prompt/source text.

**Direction (v4 addition):** `direction ∈ {long, short, both}`. `'short'` when the user asks what to short/bet against, or expresses a bearish thesis they want to profit from; `'both'` when they want the two sides of the trade (5 longs + 5 shorts, `/select` runs once per lens). Default `'long'`. The thesis-review card shows a Long/Short/Both toggle so the user can override the extraction. **Intent (v4 change):** the `intent` field is still extracted, but the UI no longer exposes an intent toggle — the product always behaves as "conviction in specific assets": named assets are resolved against the DB, force-included in the candidates, and anchor-scored; theses without named assets simply have no anchors and degrade naturally to thematic behavior. Direction changes the MEANING of the ranking, not the retrieval: candidates are still fetched by semantic similarity (the assets hurt by a thesis live in its semantic neighborhood — disrupted incumbents, losing competitors), and `/select` then scores **negative exposure**: s=100 means the thesis directly implies this asset's decline; the best shorts rank first. `/analysis` reframes to evidence → mechanism of harm → shorting caveat (borrow/squeeze/timing risk). Audits and binding requirements apply identically in both directions.
**Strategies — goal-seeking theses (2026-07-10).** Some documents state a GOAL rather than a directional view on named assets: "hedge against the dollar", "protect against inflation", "generate income". A goal admits several distinct strategy families (a dollar hedge → precious metals, non-USD currencies, Bitcoin/hard-asset crypto, inflation-linked bonds, non-US equities); a directional thesis ("NVDA wins AI") mostly does not — and a run that converges on the single best expression (gold, gold, gold) hides the alternatives the user implicitly asked about. `/thesis` therefore extracts `strategies: []` — 2–5 MUTUALLY DISTINCT avenues that each independently express the goal, ≤5 words each, in English — ONLY when the document is goal-seeking; `[]` for directional theses. Strategies are not themes: themes are facets of one topic and all get searched; strategies are alternative ANSWERS the user could choose between. They feed the Breadth control (§6) and, in Diversified runs, the retrieval fan-out and strategy allocation in `/select` (§5.3). Extraction honesty: a goal with one real expression returns `[]` or a single entry and the run degrades to standard behavior — strategies are never padded into existence.

**Regex narrowing (2026-07-07):** the offline extractor's general stock trigger no longer fires on `company/companies` — "I want to invest in the companies that benefit" names beneficiaries, not an asset class, and the word was silently binding stocks-only (dropping e.g. a tokenized-SpaceX anchor). Inside an explicit "only …" clause the word still binds ("only European companies" = stocks-only), and "stocks/equities/shares" keep binding everywhere — same explicitness bar as the doc-warnings rule (§5.4).

**Regex narrowing II — currency mentions & goal statements (2026-07-10, found by the strategy-breadth E2E):** two offline-extractor false positives surfaced on the flagship goal-seeking prompt "I want to hedge against the US dollar": (a) **currency mentions bound regions** — "US dollar"/"U.S. dollar" matched the US-market trigger and produced a binding `region_set=['us']`, which pre-seeded the Markets seg to USA-only AND armed the compliance auditor's `region` code; the auditor then deleted the non-USD currency ETFs (FXC, FXA) and the international-equity pick (DFIV) — precisely the alternative strategies a dollar hedge asks for. The region triggers now carry a negative lookahead: us/u.s./america(n)/united states followed by "dollar(s)" names a CURRENCY, never a market scope (both the general trigger and the "only …" clause trigger). (b) **goal statements became semantic scope** — the offline extractor set `constraint_note` to the instruction-sentence blob whenever ANY soft cue fired ("I want …"), handing the auditor a semantic constraint made of the thesis topic: the §5.4 topic-leak hazard, fixed for the LLM extractor in PR #40 but still live in the offline path. The offline `constraint_note` now requires a genuine RESTRICTION cue in the instruction sentences (only/exclude/without/avoid/nothing but/exclusively/restrict/limit to + Italian equivalents); goal statements and soft wishes never become semantic scope. Real restrictions ("only crypto related to the Ethereum ecosystem") keep binding exactly as before.

**Regex narrowing III — negated mentions (2026-10-05):** the class/region/cap triggers matched a word wherever it appeared, so a negated mention became a REQUIRED value: "ETFs only, no single stocks" put stocks back into an ETF-only request (the offline result replaces the LLM's under the same-source merge), "only stocks not listed in China" bound China-only, "non-US stocks" bound US-only, "no small caps" bound small caps. `stripNegations` now removes a negation cue (no/not/nor/n't/without/excluding/except/never/avoid/other than/rather than/instead of) plus up to four following words, stopping at punctuation, before those triggers run; "non-"/"ex-" drop only the word they attach to, and "not only/not just" is not a negation. Exclusion tags still read the full text ("no defense"), and the instruction sentence still reaches the auditor verbatim as `constraint_note`. The LLM side normalizes plural/synonym answers ("stocks", "ETFs", "equities", "US", "Large-cap") instead of dropping them, since a dropped class made a binding set narrower than the request.

**Beginner / low-risk first screen (2026-07-14).** A financial adviser leads a new or explicitly low-risk investor toward ETFs first, and the product now mirrors that. When the document reads as a beginner or a low-risk / conservative mandate ("I'm new to investing", "I want something safe", "low-risk", "risk-averse", Italian "principiante" / "basso rischio") AND the thesis names no specific assets (no anchors) AND no asset class was otherwise extracted, `/thesis` defaults `docCrit.asset_set = ['etf']` so the FIRST screen returns ETFs only — the class advisers steer new, low-risk investors toward, and what today's financial assistants mostly offer that profile. It is a default, not a hard rule: it seeds the review-card Asset seg like any doc-derived constraint, and the user broadens it (Asset seg → any/all kinds) and re-runs to widen the universe — a re-run posts an explicit `cardCrit` that REPLACES the default under the exclusive-merge semantics, so this only shapes the first run. Two guards keep it from hijacking a real thesis: a named asset ("NVDA is a low-risk play") keeps its anchor and asset class (the no-anchors guard), and an explicit asset request ("low-risk tech stocks") keeps stocks (the empty-asset_set guard). Deterministic (`isBeginnerOrLowRisk` / `applyBeginnerEtfDefault` in requirements.ts), so no extra LLM cost.

**Port verbatim from v3:** the dual-extractor union (LLM + deterministic regex on instruction sentences), **exclusive-merge semantics** ("only X" REPLACES, never unions; restrictive fields last-writer-wins; exclusions additive), the `semantic` requirement field for meaning-level scope ("related to the Ethereum ecosystem"), and the thesis-card mismatch alarm. Anchors now resolve against the DB (`ilike` name/ticker match), not a hand list.

### 5.2 `/candidates` — hard filter + semantic retrieval (replaces whole-catalog prompting)
1. **SQL hard filter** from requirements — this is where "MUST be followed" lives:
```sql
select a.id, a.ticker, a.name, a.kind, a.region, a.cap_class, a.exchange,
       a.cex_venues, a.dex_venues, a.sector, a.categories, a.etf_portfolio,
       a.volume_24h_usd,
       left(a.description, 300) as blurb,
       1 - (e.embedding <=> $thesis_embedding) as sim
from assets a join asset_embeddings e on e.asset_id = a.id
where a.is_active
  and a.accessibility = 'open'
  and ($asset_set   is null or a.kind      = any($asset_set))
  and ($region_set  is null or a.kind='crypto' or a.region = any($region_set))
  and ($cap_set     is null or a.kind in ('etf','bond') or a.cap_class = any($cap_set))
  and ($cex_only    is false or a.kind<>'crypto' or cardinality(a.cex_venues) > 0)
  and ($cn_hkex_only is false or a.kind='crypto' or a.region<>'cn' or upper(coalesce(a.exchange,'')) in ('HK','HKEX','HKSE'))
  and (a.kind<>'crypto' or a.volume_24h_usd is null or a.volume_24h_usd >= 100000)
  and not (a.ticker = any($exclude_tickers))
order by e.embedding <=> $thesis_embedding
limit 100;
```
**HKEX venue normalization (2026-07-12):** FMP persists Hong Kong listings as `exchange='HKSE'`. The SQL filter, runtime fallback, and deterministic audit accept `HKSE` plus the legacy aliases `HK`/`HKEX`. While an older SQL function is still deployed, a zero-row `cn_hkex_only` response is retried without the stale server-side flag and narrowed locally, preventing false empty China screens during rollout.

2. Thesis retrieval context = a compact English thesis packet (`summary`, `stance`, ordered `themes`, anchors/private entities, direction). Retrieval fans out across up to 6 Voyage queries, assembled in PRIORITY order — the full thesis packet, then for short/both mode a negative-exposure query ("disrupted incumbents/direct losers"), then direct/adjacent anchor exposure, then the top themes filling the remaining slots (2026-07-08: the negative-exposure and anchor queries outrank the theme fill; previously the negative query was appended last and the 6-query cap silently dropped it on exactly the richest short theses — 4+ themes with anchors. Themes are the safest to trim: the full packet already embeds every theme). The primary query fetches 400 rows; secondary queries fetch 180 each; candidates merge by asset id with reciprocal-rank-style score fusion before the final top-100 cut. This keeps the original hard-filter guarantees while rescuing assets that only match one subtheme or the short-side lens.
   **Statement-timeout resilience (2026-07-12):** if a pgvector RPC exceeds the database statement budget, that query retries once with a smaller pool (primary 200, secondary 100). A second timeout drops only that retrieval facet when at least one other thesis/theme query succeeded; if every facet times out, the run still fails visibly instead of returning a false honest-empty state.
3. If the semantic requirement names an ecosystem/category, add a soft boost: candidates whose sector/name/categories match a small synonym-expanded scope (`Ethereum` ↔ `ETH`/`EVM`/`rollup`, `AI` ↔ `artificial intelligence`/`GPU`/`compute`, etc.) get `sim + 0.15` before the cut (boost, not filter — the compliance audit enforces the hard version).
**Tokenized-clone retrieval filter (2026-07-08).** CoinGecko carries hundreds of tokenized TradFi clones — "Tesla xStock", "SPDR S&P 500 ETF Trust Defichain", "(Ondo Tokenized ETF)" lines whose descriptions are near-perfect embedding matches for any stock/ETF-flavored thesis ("Diversified Crypto ETFs in USA" filled its pool with clones and crowded out the real GDLC/NCIQ index funds). Retrieval drops crypto rows identified as clones — `categories` containing "tokenized", or a name carrying a tokenization marker (tokenized/xStock/bStocks/(Backpack) or a TradFi issuer/wrapper word: iShares/SPDR/Vanguard/Invesco/Xtrackers/ETF) — UNLESS the thesis itself is about tokenization (thesis text or semantic scope matching tokenized/RWA/real-world assets/xStock/on-chain equities), in which case clones stay eligible. Scope: retrieval only — anchor resolution and `ensureAnchors` are untouched, so a named unlisted company still resolves to its tokenized line (the SpaceX-before-IPO path) and force-included anchors still surface. The real DeFiChain L1 coin (DFI) is not caught: the bare word "defichain" is deliberately NOT a marker — clone names betray themselves via the issuer/ETF words instead.

**Crypto liquidity screen (24h volume).** Crypto rows whose 24h trading volume is a known value below **$100k** are hard-filtered out of the candidate universe — thin, illiquid coins are a liquidity risk and never reach retrieval, mirroring the `cex_only` gate. Sourced from CoinGecko `total_volume` (USD) captured at ingest into `volume_24h_usd`. NULL passes (only a *known* sub-$100k volume excludes), so crypto keeps surfacing before a re-ingest backfills the column and the screen tightens automatically as volumes populate. Crypto only; equities/funds have no `volume_24h_usd` and pass. Shown on crypto pick cards next to Market cap. Anchors are unaffected (`ensureAnchors` force-includes named assets after the SQL filter). Mirrored in `match_candidates`.

4. Zero rows → return the **"nothing matched your requirements"** state (frontend renders the v3 screen). No relaxation, ever.

**Cap filters don't apply to funds (2026-07-08).** An ETF/bond-ETF row's `cap_class` bands the fund's own AUM, not the market caps of what it holds — so a binding cap requirement applied to fund rows means "funds of this SIZE", never "funds holding stocks of this size". Observed failure: a "S&P 600 Small Cap ETF" thesis extracted `cap_set=['small']`, which hard-filtered the fund universe to boutique $300M–$2B-AUM products and silently excluded every flagship tracker (IJR $103B AUM, SPSM $16B, IJT, SLYG…) — including IJR as a force-included anchor, since binding filters win over mentions. Cap-class words in a thesis describe the underlying exposure; for funds that exposure lives in the name/description/`etf_portfolio` and is judged semantically by retrieval, `/select`, and the compliance audit. Deterministic rule, mirrored in `match_candidates` and `passesFilters`: **`cap_set` constrains `stock` and `crypto` rows only; `etf`/`bond` rows pass through.** (The `micro` exclusion tag still applies to funds — excluding sub-$300M-AUM products is a liquidity screen, not an exposure claim.)

### 5.3 `/select` — Claude rerank (v3 `llmSelect`, adapted)
Input: the same compact English thesis packet used for retrieval (not raw source text), binding-requirements summary, and the ≤100 candidates as compact lines (`ticker|name|kind|region|sector|categories|portfolio — blurb`, where `portfolio` (PR #10) is the shared `portfolioLine` helper's `holds <top-5 sym+name>; sectors <top-4>` segment for ETFs, empty otherwise; `/analysis` reuses the same helper holdings-only so the two prompts never drift). Raw document text remains available to the compliance audit only. Output: `[{t, s(0–100 absolute), w(2 sentences), r(anchor|complement|competitor|adjacent)}]`, max 10, `s≥35` or omit, `[]` if nothing genuinely relates. Port v3 rules verbatim: judge by meaning; binding requirements MUST NOT be violated; competitors of anchors flagged; fewer than 10 is correct when true. Validate every ticker against the candidate set — anything else is discarded.

**Hybrid mix when asset type is unconstrained (2026-07-07).** When the merged requirements carry no asset-type restriction (nothing from the document, the plain-language box, the card selector, or the interview), `/select` aims for a balanced result: the prompt asks for 3–4 genuinely related picks from each kind present in the catalog, and a deterministic pass then caps each kind at 4 (2 when `maxPicks < 8`, i.e. per-lens in 'both' mode), keeping the total ≤ maxPicks by score. Honesty rule unchanged: a kind with no genuine matches is not padded — fewer picks is the correct outcome. Any explicit asset restriction disables balancing entirely.

**Size data in the catalog lines (2026-07-23).** Same doctrine as the §5.4/§5.5 fixes, third location: `/select`'s "w" rationales invented AUM figures the catalog never showed (a live run wrote "~$22B AUM" for SMH, actual ~$70B, and "~$12B" for SOXX, actual ~$46B). Both catalog line shapes — the main selection and the scarcity top-up — now carry the shared §5.4 `sizeBand()` field after `kind`, and the main prompt pins any size claim in a rationale to the shown band (no precise figures; no size claims for unbanded lines).

**Minimum shortlist of 5 (2026-07-08).** A run that passes the hard filters should never feel empty: when fewer than 5 picks clear the s>=35 bar, `/select` fills the shortlist with the closest *stretch* candidates at their honest sub-35 scores — the prompt asks for honest low scores instead of omission, a deterministic pass fills to the floor (5 for full runs; 3 per lens in 'both' mode, so >=6 combined — flooring each 5-pick lens at 5 would force every 'both' run to a padded 5+5) from that stretch pool most-aligned first (in scarcity the per-kind/theme caps do not block the fill), and if the model returned fewer total entries than the floor, ONE follow-up scoring call ranks the closest remaining candidates (sim-ordered, top 25) honestly and fills from those — best-effort: a failed top-up never fails the run. Scores are never inflated: a 25-score card reads as a stretch on its face. Hard filters and both audits still win — stretch picks pass the same deterministic + compliance audits, so a run can still end below 5, or empty, when the requirements truly exclude the universe. Rationale: "Diversified Crypto ETFs in USA" returned a single pick — honest, but useless as a research starting point.

**Low-priority crypto score cap (2026-07-08).** Meme coins and stablecoins/stablecoin protocols are allowed to appear when they are in-scope, but they should not outrank core thesis assets: after LLM scoring, any `kind='crypto'` row whose ticker/name/sector/categories mark it as meme/memecoin or stablecoin is capped at `s<=50` before sorting and before any stretch top-up. This is a ranking demotion, not a filter — users still see the asset when relevant, but it stays visibly low-priority. **Exception — on-topic escape (same doctrine as the §5.2 tokenized-clone hatch):** when the thesis itself is about the capped class (thesis packet or themes mention stablecoins for the stablecoin cap, memes for the meme cap), the cap is skipped for that class only — a stablecoin-infrastructure thesis must rank stablecoins by genuine fit ("Morgan Stanley stablecoin reserve fund" would otherwise flatten USAT 72/PYUSD 62/USD1 58 into a 50-tie while non-stablecoin BUIDL keeps 88).

**Subtheme diversification (2026-07-08).** After LLM scoring and the asset-kind cap, a deterministic pass caps repeated first-category/sector clusters (3 per cluster for 10-pick runs, 2 per cluster in 5-pick lens runs) before filling any remaining slots with overflow. This reduces same-subtheme crowding without fabricating relevance or changing scores.

**Strategy breadth — Diversified runs (2026-07-10).** When the run is Diversified (§6: the Breadth seg, offered when `/thesis` extracted ≥2 strategies and pre-set to Focused — Diversified is the explicit opt-in since 2026-07-10, user decision; the user's selection is the final word), the shortlist must COVER the strategies instead of converging on the single best expression — observed failure: "hedge against the dollar" returned only gold expressions. Mechanics, single-lens runs only ('both' mode keeps standard behavior — two 5-pick lenses are too small to sub-allocate): (a) **retrieval** — the strategies take the theme slots in the §5.2 query priority order (packet → negative → anchors → strategies), so every avenue has candidates in the pool before selection can consider them; (b) **`/select`** — the prompt lists the strategies and asks for 1–3 genuinely related picks PER strategy, each entry carrying `g` = the strategy it expresses, validated against the list (an unmatched/missing `g` lands in an "other" group); (c) **deterministic allocation** replaces the per-kind hybrid cap and subtheme diversification for the run (a strategy legitimately expressed all-ETF must not be truncated by the kind cap): each strategy caps at 3 picks, and when the total exceeds maxPicks the trim keeps each covered strategy's best pick first, then fills by score. The minimum-shortlist floor stays PER-RUN, never per-strategy — the stretch machinery must not pad every weak avenue to 5. Honesty unchanged: scores stay ABSOLUTE — gold at 95 next to a currency hedge at 55 is the useful answer ("gold is the strong play, these are the alternatives"), never a flattened tie; a strategy with no genuine picks simply doesn't appear. Focused mode, no/one extracted strategy, or 'both' direction = today's behavior exactly.

**Ten distinct companies (2026-07-07).** Before `/select`, the candidate catalog is deduplicated per company (key: kind + normalized name; the primary line = anchor ticker > non-OTC exchange > higher similarity), so the ≤10 pick slots always go to distinct companies — BIDU and BAIDF can no longer consume two slots. After both audits and analysis, sibling listings re-join the picks: inserted right after their primary with the same score/why/analysis (each sibling must still pass the deterministic hard filters, e.g. cn_hkex_only), and the UI's same-company collapse (§6) renders them behind the "n options" button. The "Final: N" status line counts companies. **HKEX venue normalization (2026-07-11):** FMP stores Hong Kong listings with `exchange='HKSE'`; `cn_hkex_only` therefore accepts `HKSE` as well as the legacy normalized aliases `HK`/`HKEX`. This fixes explicit-China screens incorrectly filtering out every FMP HKEX row.

**Ecosystem scope is not an anchor (2026-07-08).** "Assets on Ethereum" asks for the assets LIVING in that ecosystem, not for ETH itself — but the extractor anchored the chain's token (force-include + near-top placement) whenever the chain was named. Two guards: (a) the `/thesis` anchors instruction states that a blockchain/platform naming WHERE assets live ("assets on Ethereum", "tokens in the Solana ecosystem", "protocols on Base") is venue scope, not an anchor — it belongs in `requirements.semantic`; a chain token is anchored only when the thesis bets on the asset itself ("ETH will outperform"); (b) the `/select` prompt carries the mirror rule — under an on/within-ecosystem thesis the native token is not a genuine match unless explicitly bet on.

**Named assets rank by judgment, not fiat (2026-07-07).** The v3 anchor score floor (`s = max(s, 90)` on long theses) is removed. Instead: (a) anchor extraction covers assets the document explicitly names as *central* — whether to bet on or against them (a bearish "Strategy's BTC sales pressure Bitcoin" makes BTC and MSTR anchors); (b) anchors stay force-included in the candidate pool; (c) the rerank prompt states that an explicitly named central asset is usually the thesis's most direct expression (long) or most direct victim (short) and belongs at or near the top *unless the document treats it as a passing mention* — top placement emerges from judgment, exceptions stay honest. Structured calls (`/thesis`, `/select`, compliance audit, Polymarket queries+rerank) run at temperature 0.2 — run-to-run rerank variance at the default 1.0 was observed dropping a thesis's own named asset from the results entirely. `/analysis` prose keeps the default. `resolveAnchors` orders name matches by market cap so ambiguous prefixes resolve to the major, not an arbitrary row, and tries parenthetical former names first ("Strategy (formerly MicroStrategy)" → the more specific "MicroStrategy" wins the prefix round over a bare "Strategy%", which would grab an unrelated "Strategy Shares…" ETF); extraction is told to keep the widely-recognized name for rebrands.

### 5.4 `/audit` — both v3 exit audits, unchanged
1. **Deterministic:** re-check every pick against the requirement object in code (kind/region/cap/venue/exclusions). Violators dropped, logged, surfaced in the UI status line.
2. **Compliance (LLM):** picks + the user's literal instruction sentences → `{violations:[{t, c, why}]}`, where `c` is a violation code from a closed set; flagged picks dropped with the reason shown. Enforces semantic scope (ecosystems etc.). Skipped entirely when the merged `Crit` carries no enforceable constraint.

**Hierarchical scope + full category context (2026-07-08).** The compliance auditor was shown only `(kind, sector-or-first-category)` per pick, and CoinGecko's PRIMARY category becomes the sector at ingest — so PERP/DDX appeared as "(crypto, Decentralized Exchange (DEX))" against an "only DeFi protocols" requirement and were flagged "DEX, not DeFi protocol", even though both carry "Decentralized Finance (DeFi)" two tags down. Two fixes: the pick lines now carry sector + up to 6 categories (one pick per line), and the prompt states that category labels are hierarchical — a DEX/AMM/lending/derivatives/staking/stablecoin protocol IS a DeFi protocol, an L2 belongs to its base chain's ecosystem, a sector ETF to its sector — so a pick is never flagged for being a SUBCATEGORY of the requested scope.

**Constraint violations vs thesis fit (2026-07-10).** A run on a European AI-compute-independence paper had five broad-Europe ETFs (FLEE, SPEU, IEUR, DBEU, EZU) deleted by the compliance auditor, each with the reason "Broad Europe ETF, not AI compute independence themed". None of them violated a requirement — they were *weak fits*, and fit is a `/select` score, not a compliance verdict. The auditor exists to enforce what the user said may appear in the results; it must not adjudicate how well a pick expresses the thesis. Two causes, two fixes:

- **The thesis topic leaked into the scope field.** `requirements.semantic` is for a scope RESTRICTION the user states that the structured fields cannot express ("only crypto related to the Ethereum ecosystem"). The extractor was writing the document's SUBJECT there instead, and `constraint_note` then reaches the auditor under the header "the user's own requirements — enforce strictly", which no prompt caveat can outrank. The `/thesis` prompt now states that a document's topic or theme is never a semantic scope — topics belong in `summary`/`themes`, where they already drive retrieval and scoring — and `semantic` is populated only when the user restricts what may appear in the results.
- **Free-text violation reasons could not be checked.** The auditor returned `{t, why}` with `why` as prose, so "not AI compute independence themed" passed through unexamined. It now returns `{t, c, why}` where `c` is a code from a closed set — `asset_type | region | cap | venue | exclusion | ticker | semantic` — and a violation is discarded in code unless its code names a constraint actually present on the merged `Crit` (`region` requires `region_set`, `semantic` requires `constraint_note`, and so on). There is no code for "off-theme", so a fit objection has nowhere to land. When `Crit` carries no enforceable constraint the auditor is skipped altogether, saving an LLM call on unconstrained runs; the document's instruction-like sentences stay corroborating context for constraints already in `Crit` and are never an independent source of them.

Thesis fit is already expressed, and always was: `/select` scores 0–100 honestly (stretch picks below 35, §5.3) and the result card bands that score into High (≥70) / Medium (≥40) / Low alignment beside the gauge (§6), with a stretch caveat line under it. A weakly-related pick must therefore SURVIVE both audits and present itself as a low-scored stretch — the user decides whether to keep it. Deleting it as a "compliance" failure hid that decision behind an alarming status line, and fought §5.3's minimum-shortlist floor, whose entire job is to add exactly those stretch picks.

**Size data in the audit lines (2026-07-23).** A "global tech ETFs with AUM above 10 billion" screen came back with ZERO picks: the quantitative half of the requirement reaches the auditor as `constraint_note` (the `semantic` code), but the pick lines carried no size data at all — so the auditor guessed dollar figures from fund names and flagged every ETF "AUM not clearly above $10 billion threshold", including trackers whose AUM is far past it (the same starved-auditor failure mode as the 2026-07-08 category fix, now for numbers). Same doctrine, two fixes: (a) each pick line now carries the SIZE its row's `cap_class` already bands (§4.1 boundaries rendered as a dollar range — fund AUM for `etf`/`bond` rows per the 2026-07-08 rule, market cap otherwise; omitted when `cap_class` is null); (b) the prompt states that size/market-cap/AUM requirements are judged ONLY from the shown range — a pick whose shown range satisfies the requirement is never a size violation, a line with no size is never flagged on size alone, and the model must never estimate size from a name or its own knowledge. The bands are coarse ($10B–$200B, not exact AUM), which is exactly enough for round-number thresholds like the ones users write; a requirement finer than the bands ("AUM above 47 billion") honestly cannot be verified and therefore cannot drop a pick. Zero-pick runs stay legitimate when the requirements truly exclude the universe (§5.3) — this fix only stops the auditor from inventing the exclusion.

**Document warnings never bind (2026-07-07).** The regex that harvests instruction sentences can't tell an author's risk warning from a directive: a YouTube transcript's "companies must avoid liability from Chinese-origin models" was fed to the compliance auditor as the user's instructions and dropped four China ETFs. The auditor now receives two separated inputs — the user's OWN merged requirements (structured summary + plain-language box + semantic note: enforced strictly) and the document's instruction-like sentences (bind ONLY when they clearly state what the results should contain/exclude; risk warnings, disclaimers, legal language, and author-to-audience advice never cause a flag — if the user wants such constraints they add them explicitly). The thesis-extraction prompt carries the same guard for docCrit.

### 5.5 `/analysis` — v3 analysis pass, unchanged
Final picks only, full budget: per pick 3 sentences — evidence (quote/paraphrase the user's own phrasing), mechanism (what it does, who pays it, what drives value), fit-or-caveat. Filler phrases banned; varied structure.

**Size data in the analysis lines (2026-07-23).** Same doctrine as the §5.4 audit fix, display half: without size data the prose stage invented figures (a live run described SMH, AUM ~$70B, as "AUM sits near the $10B threshold"). Each pick line now carries a `size` field — the row's `cap_class` rendered as the shared §5.4 dollar band (fund AUM for `etf`/`bond`, market cap otherwise, empty when unbanded; one `sizeBand()` helper in candidates.ts feeds both prompts so they never drift) — and the prompt requires any size claim to stay within the shown band, forbids precise figures, and forbids size claims for picks whose field is empty.

### 5.6 `/market` — real data (replaces simulated + web-search prices)
- Stocks/ETFs/bonds: FMP delayed quote (`/stable/quote`) + 30 trading days EOD closes (`/stable/historical-price-eod/light`). (Legacy `source='eodhd'` rows keep the EODHD path until retired.)
- Crypto: CoinGecko `market_chart?days=30` + current price.
- Pre-IPO (`source='sacra'`, 2026-07-10): **no live quote exists** — return `price:null, series:[]` with `marketCap` = the stored estimated valuation and `asOf` = the row's `updated_at`; the card shows the valuation and a "private — est. valuation" note instead of a price. Never call a quote vendor for these rows (and never let them fall into the crypto branch).
- Response per asset: `{price, change1d, change30d, marketCap, series[30], currency, asOf, delayed:bool, yearHigh, yearLow}`.
- **Snapshot fallback (2026-07-28).** The market layer is not persisted: these endpoints are called live on every run behind only a 60s in-process cache, so a failed vendor call left the equity card empty. `assets.market_snapshot` (`db/market_snapshot.sql`) holds one stored capture per equity, written by `npm run snapshot:market`; store only what your data license allows. It is a **fallback, not a cache**: `marketFor` still calls the vendor first and reads the column only when that call fails — including when no `FMP_KEY` is set, since `fmpKey()` throws inside the fetch and lands in the same catch, so no separate branch exists. The snapshot is produced by `fmpEquityMarket` itself and mapped by the shared pure `mapFmpMarket`, so the stored payload is by construction what the live path would have returned; a second hand-written mapping would drift the moment either side gained a field. Deliberately **not** built on the bulk CSV endpoints — they are a different code path with their own rate limiter and a blank-cell-parses-as-zero trap, and a fake `0` P/E wins every lowest-P/E ranking. Rows whose calls fail stay `null` rather than being written empty: null means "no snapshot, degrade honestly", an empty payload would assert "this asset has no market data". **Staleness is surfaced, never hidden** — `stale:true` on the response, the sparkline label becomes `30 days to <date>` instead of "30 day price history", and the price tile reads `as of <date> · snapshot` where a live quote says `· delayed`.
- **Quote-field surfacing (2026-07-12):** the FMP quote we already fetch carries more than price — `changePercentage` (1 trading day), `yearHigh`/`yearLow` (52-week range) are passed through as `change1d`/`yearHigh`/`yearLow` at zero extra calls. Crypto `change1d` is computed from the last two daily closes of the `market_chart` series we already fetch (≈24h move); crypto has no 52-week fields (30-day window only) and pre-IPO rows have all three null. The card shows the 1-day and 30-day moves side by side (each colored by its own sign) and a 52-week range bar with the current price marked.
- Sparklines render the **true** series; the SIM/LIVE~ tagging system is retired in favor of `asOf` timestamps ("delayed up to 15 min" where applicable). Cache 60s in the Edge Function. Vendor failure → card renders with "—" and a data-unavailable note; **never** fabricate numbers.
- **Kind-specific financial data — `fin` (2026-07-13):** the response gains an optional `fin` object holding everything else the vendors give us for free, feeding the detailed-analysis Financial data table (§6). Equities: the quote we already fetch also carries `open`, `previousClose`, `dayLow`/`dayHigh`, `volume`, `priceAvg50`/`priceAvg200` — passed through at zero extra calls. Stocks additionally make **one `stable/ratios-ttm` call per pick** (FMP Ultimate has no daily quota; ≤10 picks per run): P/E, EPS (netIncomePerShare), price/sales, price/book, debt/equity, dividend yield, gross + net margin. Crypto: **one batch `coins/markets?ids=…` call per run** covering every crypto pick (CoinGecko demo tier, cached 60s per id): market-cap rank, FDV, circulating/total/max supply, 24h high/low, ATH + distance from it, ATL; plus 7-day and 30-day **average daily volume** computed from the `total_volumes` array that already rides the `market_chart` response we fetch for the sparkline. Every `fin` field is nullable and omitted when the vendor doesn't return it; ratios/batch failures degrade to a fin-less response, never break the card. Pre-IPO rows have no `fin`.

### 5.6b Outbound links per card (added 2026-07-09, staging)
Each result card carries up to two deep links, built in `runtime/links.ts` (`assetLinks`) and attached by the server to each pick as `{website, platform}`:
- **platform** — a public page with full financial info, derived from ids we already store (no extra storage, never lags a re-crawl): crypto → `coingecko.com/en/coins/{vendor_id}`; stock/ETF → Yahoo Finance `finance.yahoo.com/quote/{sym}`. For `source='fmp'` rows `sym` **is** `vendor_id` verbatim — FMP symbols are already Yahoo-format (US bare, `.MI`/`.L`/`.DE`/… suffixes, HK zero-padded `0700.HK`). Legacy `source='eodhd'` rows keep the EODHD-code→Yahoo-suffix map (`US`→bare, `LSE`→`.L`, `XETRA`→`.DE`, `AS/PA/BR/LS/MC/SW/VI/IR/ST/CO/HE/OL` alike, `HK`→zero-padded); an unmapped exchange falls back to a Yahoo `lookup?s={ticker}` so a link never resolves to the wrong quote. Bonds have no reliable public page → no platform link.
- **website** — the project's/company's own site, stored at ingest in `assets.website_url` (CoinGecko `links.homepage[0]`; FMP `profile.website`) — both already fetched, so zero extra vendor cost. Nullable and backward-compatible; existing rows fill in over the nightly crypto-detail and equity-fundamentals refresh cycles. Both links are best-effort — omitted (not guessed) when a reliable URL can't be built.
- **logo** (2026-07-13) — each card shows the asset's logo next to its name, from `assets.logo_url` (schema §3), attached to the pick payload as `logo`. Vendor CDN images are hotlinked, never downloaded or stored as files. Client fallback chain: `logo_url` → website favicon (Google s2 service off `website`'s hostname — covers Sacra privates, whose vendor has no logos) → ticker-initials monogram. A broken image degrades to the monogram via an error handler, never a broken-image icon. Backfill: crypto in ~12 `coins/markets` calls (`npm run backfill:logos`, BF_SOURCE=coingecko); equities fill via the nightly profile re-crawl (~6-day cycle) or `BF_SOURCE=fmp` with a budget cap.

### 5.8 Prediction markets — Polymarket (added 2026-07-06, staging)
A "Prediction markets" section in the results: the thesis is matched against live Polymarket bets, same path as assets — retrieve → LLM rerank by meaning → aligned side. Example: "temperature will rise in Europe" → "Paris heat wave by July 31?", side YES.

- **Retrieval** (`runtime/polymarket.ts`): one small LLM call turns the thesis summary + themes into 3–5 short search queries in prediction-market phrasing (falls back to the themes verbatim on LLM failure); each query hits the public Gamma API `GET /public-search?q=…&events_status=active` (no key needed); events→markets are flattened, closed/inactive filtered out, deduped by market id, sorted by volume, capped at 40 candidates.
- **Rerank**: one LLM call judges genuine relevance to the thesis (meaning, not keywords — same principle as `/select`), returns up to 5 picks with a 0–100 relevance score, a one-line why, and `side` = the outcome that pays out if the user's view proves correct (works for long and short theses alike). Returns [] honestly when nothing genuinely relates.
- **Orchestration**: runs concurrently with the asset pipeline inside `/api/complete` (thesis-only input); failures degrade to an empty list and never break the asset results. Result payload gains `predictions[]` (question, event title, polymarket.com URL, outcomes + implied probabilities, aligned side, score, why, volume, end date).
- **UI**: results page renders a "Prediction markets — Polymarket" section after the asset cards when `predictions` is non-empty; each bet card shows the question, the outcome pills (the LEADING outcome — highest implied probability — is the highlighted one, 2026-07-08; the user's aligned side is stated in the why-line header "if your thesis plays out → X"), the why-line, volume, end date, and a link to the market. Bets are informational parity with picks: same honesty rules, no padding.
- **Ladder-side consistency (2026-07-08)**: observed rerank slip — a bullish "ETH new all-time high" thesis got side YES on the $4k/$4.5k/$5k reach-rungs but side NO on the $3.5k rung (a new ATH necessarily crosses every lower threshold). Two guards: (a) the rerank prompt states that threshold-ladder bets for the same asset/metric must carry consistent sides — a thesis implying YES at a higher threshold implies YES at every lower one; (b) deterministically, picks are grouped by question stem (question text with numbers stripped) and when a group's sides disagree, the top-scored pick's side wins and contradicting picks are dropped (a wrong side is worse than a missing pick, same doctrine as anchors).
- **24h momentum chip (2026-07-08)**: each bet card shows the LEADING outcome's one-day move in percentage points, from Gamma's `oneDayPriceChange` (delta of outcome[0]'s implied probability, already in the `/public-search` payload — no extra request). The leader's change is only derivable when the leader IS outcome 0, or as the negation in a two-outcome market; multi-outcome markets whose leader isn't outcome 0 omit the chip rather than guess. Rendered as ▲/▼ x.x% 24h next to the leading outcome (`--up`/`--down` colors); absent/non-finite data omits the chip. Only the 1-day window is shown (decision: not week/month), and it tracks the market's leader, not the user's aligned side.
- **Bets-first ordering (2026-07-08)**: the Prediction-markets section renders BEFORE the researched asset picks when the user specifically asked for Polymarket — the source document or plain-language requirements mention "polymarket"/"prediction market", the user deliberately toggled the Polymarket seg ON in the review card, or the run is Polymarket-only. Otherwise the section keeps its default position after the asset cards. Pure frontend ordering; result payload unchanged.
- **Selectable asset (2026-07-06)**: the review card's Asset selector includes **Polymarket**. Semantics: no selection → assets + bets both searched (default); a selection including Polymarket → bets searched alongside the chosen asset kinds; a selection **without** Polymarket → bets skipped (the user explicitly scoped them out); **only** Polymarket → the asset pipeline is skipped entirely (`pmOnly` in the result; the frontend suppresses the asset empty-state and shows an honest "no related prediction markets" block when the bets also come back empty).

The first open beta runs behind Google sign-in with a daily credit budget. Signup is open — anyone with a Google account can join (2026-07-14 decision, no allowlist); the per-user daily cap is the spend guard, and the admin can zero an abuser's cap. Everything lives in Supabase and the existing Node server; no Vercel move for the beta — the custom server (`server/server.ts`, long POST-SSE runs) deploys unchanged to an always-on Node host, and the Vercel/Route-Handler refactor stays a later production milestone.

**Deploy-time switch.** Auth + credits bind only when `SUPABASE_ANON_KEY` (the publishable key) is set in the server env. Without it the app runs open, exactly as before: local dev, offline tests and CI need no accounts. `GET /api/config` tells the browser which mode the server is in.

**Sign-in.** Supabase Auth with the Google provider, PKCE flow implemented vanilla in `public/sd-auth.js` (no SDK in the browser): `/auth/v1/authorize?provider=google` with an S256 challenge, code exchange + refresh against `/auth/v1/token`, session in localStorage. The app shell stays hidden (`html:not([data-auth=ready])`) until auth settles, then either the gate (`#authGate` in `app/page.tsx`) or the app shows. No allowlist: the Google OAuth app runs in production mode so any Google account can sign in (basic email/profile scopes only, so no Google verification review is needed). 2FA is Google's concern, never ours.

**Credits (10/day, confirmed 2026-07-13).** `profiles` (credits, daily_cap default 10, credits_date, is_admin) + append-only `credit_ledger` + two SECURITY DEFINER RPCs in `db/auth_credits.sql`, execute revoked from anon/authenticated (service role only):
- `spend_credit(user, amount, reason)` — atomic row-lock, **lazy daily reset** (credits_date < today → refill to daily_cap; no cron), then check-and-decrement; amount 0 = peek. Refusal returns `{ok:false}` and charges nothing.
- `add_credit(user, amount, reason)` — grants/refunds on TODAY's balance (floors at 0); a grant evaporates at the next daily refill, a cap change is the permanent lever.
- Signup trigger creates the profile (bootstrap admin: <your admin email>, read from `app_settings.admin_email`, empty by default; see `db/auth_credits.sql`) and a `signup` ledger row. RLS: users read only their own rows.

**Charge points.** A search debits 1 credit at the START of `/api/complete` (before the SSE headers, so an out-of-credits user gets a plain 402); a failed run refunds it and the stream carries `credits` events so the sidebar pill stays live. A PDF report download debits 1 via `POST /api/pdf-credit` before the client-side print runs (the print itself costs no vendor calls — the charge is a rationing lever). `/api/thesis` and `/api/extract` require sign-in but are free. Every API fetch in `signal-desk.js` rides through `apiFetch()` which attaches the bearer token. **Cancelled runs (2026-10-05):** a run whose client goes away (closed tab, the Cancel control, a cancelled MCP call, a dropped `/v1/screen` stream) stops at its next model call or status line and frees its concurrency slot; the credit stays spent, as it did when such a run finished undelivered — refunding would let a start-and-cancel loop spend model money outside the daily budget, the single spend guard. A client gone before the charge is never charged.

**Admin.** `/admin` (app/admin/page.tsx) — server-authorized via `profiles.is_admin` on every `/api/admin/*` call: user table with today's balance/usage, per-user daily cap editor, one-day grants (negative = revoke), zero-today. Below the user table, a **Recent prompts** section (2026-07-15): the latest 100 rows of `prompt_log` newest-first via GET `/api/admin/prompts` (excerpts capped at 2,000 chars server-side with the full length shown; click a row to expand). A missing `prompt_log` table degrades to an inline note pointing at `db/prompt_log.sql`, never an error. Timezone note: the daily refresh boundary is midnight UTC (`current_date` in Postgres).

**Gate.** `npm run test:credits` — disposable auth user end-to-end against the live DB (trigger, debits, refusal-without-charge, grant/refund, lazy reset, cap change, ledger completeness); skips cleanly pre-migration, no LLM spend.

**Prompt log (user decision 2026-07-15).** Every research prompt a signed-in user submits (the /api/thesis text: typed prompt + extracted source text — never the files, which are not stored anywhere) is appended to `prompt_log` (`db/prompt_log.sql`: user_id cascade-deletes with the auth user, email, prompt capped at 100k chars, created_at; RLS on with no policies = service-role only). The insert is fire-and-forget server-side — a missing table or error never blocks the run — and a no-op when auth is off. Disclosed in the T&C (sections 4 and 6).

**User setup steps (once, before the beta):** (1) run `db/auth_credits.sql` AND `db/prompt_log.sql` in the Supabase SQL editor; (2) create the Google OAuth app (Google Cloud console → OAuth client; publish to production mode so signup is open — with only basic scopes there is no review step), paste client id/secret into Supabase Auth → Providers → Google; (3) set the app URL(s) in Supabase Auth → URL Configuration (site URL + redirect); (4) add `SUPABASE_ANON_KEY` to the server env.

## 13. Public API and MCP (2026-07-20)

**API keys (PR 1).** A key belongs to a signed-in user and spends that user's daily credits — no separate budget, and an admin zeroing a user's cap also kills their keys' spend. `db/api_keys.sql` (run once in the Supabase SQL editor, like `prompt_log.sql`): `api_keys(id, user_id → auth.users cascade, name, key_hash unique, key_prefix, created_at, last_used_at, revoked_at)`, RLS on with no policies = service-role only. Tools: `run_screen(thesis, constraints?, breadth?)` — calls `executeRun` in-process, forwards status lines as MCP progress notifications, returns the structured picks; `get_credits()` — today's balance. **Status lines ride the result too (2026-07-23):** the `run_screen` payload gains `status: string[]` — the same §5.7 transparency lines already streamed as notifications. Notifications are ephemeral and many MCP clients drop them, which left an over-constrained run's empty `picks` with no explanation; the audit-drop reasons and the "no candidate passed the final criteria check" line ARE the honest-empty story (§5.3), so they must survive into the final payload. ## 14. X bot (2026-07-21)

An X (Twitter) bot: tag @SyntheTick under a post with a request like "check the content and give me the assets" and it replies, short and professional, with the assets the post is about as $tickers plus a couple of market data points. Only SyntheTick users can use it — the mention author's X account must be linked to a SyntheTick account — and every reply spends the linked user's daily credits: same budget as the app, API and MCP, no separate metering. Three PRs to `staging`: (1) X account linking, (2) the assets endpoint, (3) the bot worker. Cost model (verified 2026-07-21 on docs.x.com): the X API is pay-per-use for new developers — the old Basic ($200/mo) and Pro subscriptions are closed to new signups. Rates: mention/timeline reads $0.010 per post returned, post reads $0.005, posting $0.015, but $0.200 when the post contains a URL — which is why every bot reply carries NO links. Empty polls return zero resources and bill nothing, so a handled mention costs ~3 cents end to end (read + parent + reply). Before go-live: buy prepaid credits AND set a spending limit in the dev portal (calls are blocked past it — the circuit breaker against bugs or deliberate bot-spamming). PRs 1 and 2 are fully testable without paying X anything.

**X account linking (PR 1).** Linking, not a sign-in method: Google stays the only way into the app; the link just maps an X identity onto an existing account, because a mention carries nothing but the author's X user id. `db/x_accounts.sql` (run once in the Supabase SQL editor, like `api_keys.sql`): `x_accounts(user_id pk → auth.users cascade, x_user_id unique, x_handle, linked_at)` — one X account per user AND one user per X account; RLS on with no policies = service-role only. Server flow in `server/xlink.ts`, OAuth 2.0 + PKCE against X, scopes `users.read tweet.read` (identity only — no offline.access, we never hold a token that acts as the user):
- `GET /api/x/link` (session-authed) → `{url}`: the X authorize URL with an S256 challenge. The `state` is an HMAC-signed blob (user id, code verifier, 10-minute expiry) keyed off `SUPABASE_SERVICE_KEY`, so the browser-redirect callback needs no server-side session store and survives restarts.
- `GET /api/x/callback` (browser redirect from X): verify state, exchange the code (HTTP Basic when `X_CLIENT_SECRET` is set — confidential client), `GET /2/users/me`, upsert the row (re-linking replaces the user's previous X account). Redirects: success `/?x=linked`; X account already linked to someone else `/?x=taken`; user cancelled on X `/?x=denied`; anything else `/?x=error`. ## 15. Financial requirements on a thesis (2026-07-28)

A thesis can carry **quantitative requirements**, and they bind like every other requirement in §5.4: *"I believe in the nuclear sector, give me ETFs with AUM above 500m"*, *"European defense ETFs with TER below 0.50% listed in EUR"*, *"Milan listed companies with market cap between 100m and 1bn and P/E below 12"*. The thesis still decides *what* the screen looks for; the requirements decide what is allowed to come back.

### 15.1 Schema

Two tables keyed to `assets`, run once in the Supabase SQL editor (`db/asset_metrics.sql`), both wholly derived from vendor bulk data and rewritten nightly: they are a cache, never a source of truth.

`asset_metrics` — **one row per asset**. Columns group by family, all nullable, never guessed: **valuation** (pe, peg, forward_pe, price_to_sales, price_to_book, ev_to_ebitda, ev_to_sales, dividend_yield_pct, market_cap_usd), **performance** (return_1d/7d/30d/ytd/1y percent, volume, avg_volume, beta), **profitability and leverage** (gross/operating/net margin pct, roe, roa, roic, debt_to_equity, current_ratio, interest_coverage, altman_z, piotroski), **growth** (revenue/earnings/fcf growth YoY), **analyst** (price_target_avg, target_upside_pct, rating_consensus, analyst_count), plus `as_of` and `source`.

`asset_prices(asset_id, date, close)` — the daily close history returns are computed from, primary key `(asset_id, date)`, retention 400 days.

**Returns are computed and written entirely inside the database** (`update_asset_returns(p_from, p_to)`), for two reasons found live on 2026-07-27. Returning them to the client does not work: PostgREST caps a set-returning function at its `max-rows` setting (1,000 here) and `.range()` cannot lift it, so a version that SELECTed the results silently updated 1,000 of 13,000 assets. And it has to be batched: the whole universe in one statement exceeds the statement timeout, so the function takes an id range and the caller walks the space, **halving any slice that times out** — asset ids are dense around 44k-50k and empty elsewhere, so a fixed slice silently loses exactly the block that matters.

**Fund fields live in `assets.etf_portfolio`, not `asset_metrics`** (they arrive with the ETF enrichment of §4.1 and were already stored). Coverage measured 2026-07-28 over 4,599 fund rows: expense ratio 4,591, inception date 4,584, average volume 4,591, sector weights 4,085, country weights 4,460, issuer 4,569, domicile 4,586. This is what makes fund requirements answerable, and it is also the **correct way to classify a fund by sector**: `assets.sector` is `null` for every etf/bond row by design (a fund's exposure is its holdings, not one label), so "energy ETFs" means a fund whose sector weights are concentrated in Energy, never a sector-column match.

### 15.2 Nightly bulk ingest (`ingest/run-metrics.ts`)

FMP's **bulk endpoints** return the whole market per call (every name verified live 2026-07-27): `ratios-ttm-bulk` (68 MB, 71,337 symbols), `key-metrics-ttm-bulk`, `profile-bulk`, `scores-bulk`, `income-statement-growth-bulk?year=&period=FY`, `cash-flow-statement-growth-bulk?year=&period=FY`, `price-target-summary-bulk`, `upgrades-downgrades-consensus-bulk`. Note **`financial-growth-bulk` does not exist** — it 404s. Coverage against our universe is 8,411 of 8,808 active stocks.

Four hard constraints, all learned by running it:

**The CSVs must stream.** A 68 MB response parsed by loading the whole body into a string is a memory spike per family, so the ingest parses line by line and keeps only the rows whose symbol matches an `assets.vendor_id`. A real CSV parser, not a line splitter: `profile-bulk` carries descriptions with commas, embedded newlines and escaped quotes.

**`part` is real pagination on some families.** It is a no-op on `ratios-ttm-bulk` (part=0 and part=1 are byte-identical), and generalizing that was wrong: `profile-bulk` part=1 and part=2 return entirely different symbols, so fetching only part=0 dropped a quarter of the universe's beta and volume (10,124 matched vs 13,380 when paged). Paged families walk `part` upward until a page is empty; the end announces itself as **HTTP 400**, which the reader treats as terminal — 4xx other than 429 never succeed on retry.

**The bulk endpoints share one aggressive rate limiter**, separate from the 3,000/min API budget. Eight families back to back returned HTTP 429 on three of them, and `income-statement-growth-bulk` exhausted its retries and landed **374 rows instead of 8,238**. Retries do not fix a limiter this coarse; the calls are spaced (`METRICS_BULK_GAP_MS`, default 12s). `eod-bulk` is the strictest: one date succeeds and an immediate second is refused, which is why returns come from our own accumulated `asset_prices` history, seeded once by `ingest/backfill-prices.ts` (13,383 symbols, ~6 minutes).

**A bulk upsert must be homogeneous.** PostgREST builds the statement from the UNION of keys across the payload and writes NULL wherever a row omits one, so a batch of naturally-varying metric rows silently clobbers columns on every re-run. The ingest tracks which families succeeded and gives every row exactly that column set: a failed family stays out of the payload and keeps its previous values.

**Prices are not split-adjusted on any FMP endpoint** (`light`, `full` and `dividend-adjusted` all serve the same discontinuity — verified on 1168.HK, 2.88 → 0.3675 across one session). Any return computed over a split window is a false spike, which is why performance requirements are a filter on a thesis rather than a ranking of the universe.

### 15.3 Requirement vocabulary and extraction

Requirements are extracted by **one cheap LLM call made in parallel with `buildThesis`**, deliberately not folded into the thesis prompt: that prompt is heavily tuned (§5.1) and adding numeric extraction to it risks the core path for a peripheral gain.

The call chooses from a **closed vocabulary** and never writes SQL or column names. Two families:

- **Company metrics**, from `asset_metrics`: market cap, P/E, price/book, price/sales, EV/EBITDA, dividend yield, revenue and earnings growth, margins, ROE, debt/equity, net debt/EBITDA, free cash flow, 30-day and 1-year return, average volume, beta, Altman Z, Piotroski.
- **Fund fields**, from `etf_portfolio` and `assets`: AUM, TER (expense ratio), track record in years (from inception date), average daily volume, listing currency, fund domicile, issuer, and **exposure weights** — a minimum percentage in a named sector or country, which is how "European defense ETFs" and "UCITS ETFs tracking India" resolve.

Each requirement is a `{metric, min?, max?}` bound, or a `{kind: sector|country, name, minWeightPct}` exposure, or a categorical set (currency, domicile). **An ask the vocabulary cannot express is reported, never dropped**: "more than 40% of revenue from foundry customers", "a buyback announced in the last 12 months", "EV exposure above 30% of revenue" and "production already online" have no vendor field behind them, so the run says so explicitly rather than returning a list that quietly ignores half the question. Individual corporate and government bonds stay out of scope per §0.

### 15.4 Enforcement

Deterministic, in code, before `/select` ever sees a candidate — the §5.4 doctrine that anything checkable must not be left to a model to guess.

**A fund's geography is what it HOLDS, for every region** (`runtime/fundgeo.ts`). `assets.region` follows domicile (§4.1a) — the right test for a company, the wrong one for a fund. Every UCITS wrapper is Irish or Luxembourgish, so a Japan ETF, an India ETF and a China ETF all carry region `eu`, and a region constraint drawn from the user's words excludes exactly the funds they asked for: "UCITS ETFs tracking India" extracted `region_set=['cn','other']` from the word "Indian" and lost NDIA.L, FLXI.DE and TIGR.MI before a single requirement ran (live 2026-07-28).

§6 already solved this for one country by tagging Italy exposure at ingest. The general rule maps a fund's own country weightings (`etf_portfolio.region_weights`, present on 4,460 of 4,599 fund rows) through the SAME buckets as domiciles, so `eu` means one thing on both sides of the test, and applies a majority rule: a fund *is* European when at least 50% of what it holds is, the same threshold the exposure requirements use. With several regions selected the rule applies to the selection as a whole (2026-10-05): a fund 45% US and 45% Europe satisfies "US or Europe". Two consequences worth stating: an Irish-domiciled S&P 500 UCITS is a **US** fund, not a European one, which is a deliberate behavior change; and a fund with no country breakdown cannot be placed, so it does not satisfy a geographic constraint. Retrieval widens the SQL region set with `us` and `eu` when funds are in scope — the buckets funds are actually domiciled in — so they survive the domicile-based prefilter long enough to be judged on holdings, the same trick §6 uses for the Italy tag. The compliance auditor is told the rule too, since it can also flag a region violation.

**Requirements are editable on the review card (§6).** They are extracted at `/api/thesis`, in parallel with `buildThesis`, so they exist before the card renders, and appear as removable chips beside Markets and Mcap. The card posts back whatever survived, and an edited set WINS over re-extraction — removing a chip is a decision, and re-reading the text would silently reinstate it. Values are re-validated server-side, so the browser can only ever narrow what the extractor found. The `unverifiable` list renders as static text in the same block, so what will not be filtered is visible before the run rather than mid-trace.

Retrieval **over-fetches** when requirements exist (the embedding pool is widened, since a hard numeric filter can cut it heavily), then each candidate is checked against every bound using `asset_metrics` and `etf_portfolio`. **An asset whose metric we do not hold is excluded** (user decision 2026-07-28): a requirement is binding, and an asset we cannot verify does not qualify. That is only honest if the gap is visible, so a §5.7 status line reports it — *"Applied 2 financial requirements: AUM above $500M, TER below 0.50%. 41 of 96 funds could be checked against both."* Zero survivors stays a legitimate answer (§5.3), and the review card shows the requirements as chips so a too-strict one is obvious and editable.

Because enforcement is deterministic, numeric requirements are **not** handed to the LLM compliance auditor; §5.4's `filterViolations` already refuses violation codes that name no real constraint, and a model second-guessing arithmetic it cannot see is exactly the failure mode that section exists to prevent.

### 15.5 Honest answers

Every screen already carries the §0 disclaimer. Requirements add three duties. The **coverage line** above, always. **Region means HQ domicile, not listing venue** (§4.1a), so "Milan listed" resolves through the Italy scope tag of §6 rather than the exchange string. And the **universe is not the world**: US, Europe, China and crypto, so Japanese and Indian *single stocks* do not exist here and a thesis asking for them is told so, while Japan and India *funds* resolve normally through country weights. Universe expansion stays a separate milestone.

### 15.6 Gate

`npm run test:requirements` — extraction fixtures over the full prompt set (each asserting the parsed bounds), the pure bound-checking layer, and a live end-to-end pass asserting that every returned asset genuinely satisfies every numeric bound, verified independently against the database rather than through the engine's own filter. Skips cleanly pre-migration; no vendor spend.

## 16. Tradable universes (2026-07-29)

A **universe** is a fixed allowlist of assets that exist as tradable tokens on an external venue; the first is `robinhood` — the 96 tokenized stocks and ETFs live on Robinhood Chain (chain id 4663). Purpose: let an external execution agent (e.g. a Sail SMA manager running Sailor) screen with SyntheTick and receive picks it can actually trade, with the token contract attached, so the agent never resolves tickers to addresses on its own. The screen is the soft bound (the agent only ever sees allowed assets); the venue-side mandate (Sail permission contracts) is the hard bound; both derive from the same registry.

**Registry.** `runtime/universe/robinhood-chain.json`, a generated file — `npm run universe:robinhood` (`ingest/robinhood-universe.ts`) rebuilds it from Robinhood's public Stock Token API (`GET api.robinhood.com/rhj/assets`, the canonical list) and verifies every entry against Robinhood Chain's Blockscout: onchain symbol must match, decimals read from chain, holder count stored as a coarse liquidity prior. Any disagreement aborts the regeneration. Prices and corporate-action multipliers are deliberately NOT stored (live values — consumers read `/rhj/prices/{symbol}` and `/rhj/assets` at execution time). Core tokens (WETH, USDG) ride along for swap-leg planning.

**Screen semantics.** `universe` is accepted by `POST /v1/screen` (top level or in `constraints`) and the MCP `run_screen` tool (`universe: 'robinhood'`). In universe mode the pipeline skips embedding retrieval entirely: the whole universe IS the candidate pool (96 ≤ the normal 100 budget), loaded from the assets table by ticker allowlist (active, open, kinds stock/etf/bond — the tokenized-clone crypto rows of the very same tokens must never match, §5.2), with `sim` carrying a holders-based liquidity prior. The anchor rescue is skipped: an anchor outside the allowlist is out, the same way other hard requirements win over mentions. Other constraints (regions, caps, finReq) still bind inside the universe. Prediction markets are excluded unless `assets` explicitly includes `polymarket` (not tradable on the venue). Screening runs on the UNDERLYING listed equities — real fundamentals, not token clones; tickers with no active DB row (currently ASML, BABA, SATS, USO — ingest gap) simply cannot be picked until fixed.

**Payload.** The result gains `universe: {name, chainId} | null`, and each pick a `token` field: `{symbol, name, address, decimals, kind, holders, logoUrl, chainId, chain, explorer} | null` from the registry.

**Thesis bar (2026-07-29 late; REMOVED FROM THE PAGE 2026-07-30).** The explorer carried a single-line composer-style bar above the table: the user typed a thesis, the page POSTed `/v1/screen` with `universe:"robinhood"` and streamed the SSE run inline, collapsing the table to score-sorted picks. User decision 2026-07-30: removed from `/universe` for now (git history holds the implementation for restoration); its slot is taken by the "How stock tokens work" explainer box below. The `/v1/screen` session-auth change shipped with it STAYS (used by the main app).

**Registry endpoint.** `GET /v1/universe/:name` returns the registry JSON — public, no key, no credit (it mirrors Robinhood's own public API and must stay readable when the caller's budget is spent; execution agents fetch it to build swap allowlists and mandates). 404 with the list of known universes for an unknown name; `cache-control: public, max-age=3600`.

Coverage is partial by the registry's own state (33 equity feeds vs 96 tokens as of 2026-07-30) — missing feeds are `oracle: null`, never guessed.

**Freshness model** (2026-07-30, answering "why do onchain columns lag"): all universe caches were fetch-on-demand, so the first request after a TTL expiry paid vendor latency, and a GeckoTerminal 429 (free tier ~30 calls/min) showed dashes until the next good fetch. Now: (1) a **background warmer** (`startUniverseWarmer()`, started by the server at boot) refreshes venue quotes, DEX data, onchain state, oracle quotes and corporate actions every 60s, so requests never pay vendor latency; (2) every fetcher **serves stale on failure** — a vendor error returns the last good snapshot up to a staleness cap (15min live data, 24h corporate actions) before degrading to null, so a 429 window no longer blanks columns; (3) the `/assets` list response carries **`asOf`** `{quotes, dex, onchain, oracle, events}` ISO timestamps from the caches, and the explorer's legend row shows when onchain and offchain data were last refreshed. Persisting snapshots to Supabase every minute was considered and rejected: nothing needs cross-restart history (charts come from the vendor), and the in-process last-good snapshot gives the same UX for free. REVISED 2026-07-31 (user decision, after a ~25min GeckoTerminal outage blanked every DEX column and the TVL/DEX tiles on prod): users must never open the page to empty onchain data. Three changes, all DEX-scoped (the other four families come from vendors that recover in seconds and were never the problem): (1) the DEX staleness cap rises from 15min to **6 hours** — the legend's "last update" line keeps the age honest; (2) the last-good DEX snapshot is **persisted to Supabase** (`universe_cache` table, one row per family key e.g. `robinhood:dex`, `db/universe_cache.sql`; written best-effort at most every 5min after a successful fetch) and loaded once at boot when the in-process cache is empty, so deploys and long outages fall back to the stored snapshot instead of dashes (still capped at 6h — beyond that, honest nulls); (3) the warmer refreshes DEX every **4 minutes** instead of every minute (fewer calls, fewer 429 cooldowns; quotes/onchain/oracle stay at 60s, corporate actions ride the 60s tick with their own 1h TTL). This is a single last-good row used as a boot/outage fallback — NOT history; the original rejection of minutely snapshot history stands.

DB-only by design: one assets query + one metrics query + the cached venue and DEX calls, `cache-control: max-age=300`. It must never fan out into per-asset vendor calls — fundamentals refresh nightly at zero marginal cost, and **live prices are the venue's job** (Robinhood's `/rhj/prices/{symbol}`, with `currentMultiplier` from `/rhj/assets`). Auth (revised 2026-07-31, user decision): the API contract keeps its key — `/assets`, `/assets/:symbol` and `/assets/:symbol/chart` require an API key or signed-in session for programmatic use (the payload redistributes ingested vendor data) — but the `/universe` explorer must work WITHOUT signing in, so **same-origin browser requests pass keyless**: a request whose `Sec-Fetch-Site` is `same-origin` (browser-controlled, not settable from JS) or whose `Referer` host matches the request host skips the key check. This is access friction, not a security boundary — anything a signed-out page renders is inherently visible to any browser, and a determined client can fake the headers; the key requirement exists to keep casual API use metered and attributable, and that survives. The bare registry at `GET /v1/universe/:name` stays fully public. No credit anywhere on these routes: DB reads, not screens.

## 18. Sail reference execution agent (2026-08-03)

**What.** `sail-agent/` is a self-contained Sailor-scaffolded project: an autonomous agent that trades the §16 Robinhood tokenized universe onchain, driven end to end by the public API. Daily loop: read SMA holdings → X recent-search news for held/watched tickers (`X_BOT_BEARER`, pay-per-use, capped by `newsMaxPostsPerTicker`/`newsMaxTickers`) → one OpenRouter thesis call → `POST /v1/screen {universe:"robinhood"}` (1 credit) → risk-tiered plan (conservative 5%/2 trades/minScore 85, balanced 10%/4/75, aggressive 20%/8/65; `agent.config.json` overrides) → bounded Uniswap V3 `exactInputSingle` swaps, strict USDG hub, max 2 per tick. Daily report to `reports/<date>.md`; chain-reconciled ledger in `.sail/memory/ledger.jsonl` (never intention-recorded — fills decoded from receipts).

**How Sail is used.** sail.money provides the custody/authorization layer: capital sits in a self-custodial Safe (SMA `0xYourSafe…`, deterministic address, chain 4663); the agent holds only a manager key whose authority is a signed onchain mandate the Sail kernel evaluates on every dispatch, fail-closed. Mandate = three permissions: buys via the shared `SwapPermissionNoOracle` singleton (`0xYourBuyTemplate…`: tokensIn=[USDG], tokensOut=21-token liquid basket, 200 USDG/tx cap), sells via a second instance of the same template, deployed from Sail's template source (GPL-2.0-or-later, fetched from github.com/sail-money/Protocol, not shipped here) at `0xYourSellInstance…` (one config per account per singleton forced the split; template's strict-coverage rule requires a ReferencePool per directional pair), approvals via bespoke `BoundedErc20Approve` (`0xYourApprovePermission…`, router-only spender). Band tolerance 600 bps — a hallucination guard, not manipulation protection; caps are blast-radius ceilings, the exact % lives off-chain. Pause = `sailor session pause`.

**How the public API is used.** `GET /v1/universe/robinhood` (public, keyless by design — §16) supplies verified token addresses for the tradable-basket generator (`scripts/gen-universe.mjs`: token has a canonical-factory Uniswap V3 USDG pool with reserve ≥ $15k → 21 of 96 qualify as of 2026-08-03) and the mandate config blobs; universe-mode screen picks carry `token.address` so the agent never resolves tickers. Venue truth (prices, halts, multipliers) reads Robinhood's public `/rhj` API directly.

**Ops.** Wire your own scheduler (see the sailor-automation skill); no trading workflow ships in this repository. A trading day is one pipeline tick followed by execution ticks that drain the plan, with `.sail/memory` persisted between runs. In CI the agent key is an encrypted keystore (export your own with `sailor keys export-ci`) supplied from a CI secret, never committed to a public repository, and unlocked via the `SAIL_PASSPHRASE` secret. App-side documentation lives in the API view ("Autonomous trading: the Sail reference agent").

**Gate.** `forge test` green (11 tests, `via_ir`); typecheck clean; mandate probes against the live chain: buy 6/6, sell 6/6, approve 5/5 (must-pass probes need a real QuoterV2-derived `amountOutMinimum` — the generator's placeholder minOut=1 is correctly denied by the band); a clean `sailor run --once` (unfunded SMA skips before any spend; funded SMA runs the pipeline and writes the report).
